微服务架构是将单体应用拆分为一组小而自治的服务，每个服务围绕业务能力构建，独立部署、独立扩展。

微服务核心原则：
1. 单一职责：每个服务专注一个业务领域，遵循 SRP 原则
2. 服务自治：每个服务独立部署、独立数据库、独立技术栈选型
3. 轻量级通信：服务间通过 RESTful API 或消息队列通信，避免 RPC 强耦合
4. 去中心化：避免共享数据库、共享代码库，每个服务自治
5. 容错性：通过熔断、降级、限流保障服务可用性
6. 演进式设计：服务可独立演进，逐步拆分优化

微服务拆分策略：
1. 按业务能力拆分：订单服务、用户服务、商品服务
2. 按领域驱动设计 DDD：识别限界上下文，每个上下文一个服务
3. 按子域拆分：将核心域、支撑域、通用域分别建设

服务间通信：
1. 同步：HTTP/REST、gRPC，适合实时性要求高的场景
2. 异步：消息队列（Kafka、RocketMQ），适合解耦和削峰
3. 事件驱动：通过事件总线实现服务间松耦合

分布式系统挑战：
1. 分布式事务：Saga 模式、TCC、本地消息表
2. 数据一致性：最终一致性 vs 强一致性
3. 服务发现：Eureka、Nacos、Consul
4. 链路追踪：Sleuth + Zipkin、SkyWalking
5. 配置管理：集中式配置中心
6. 网关：统一入口、鉴权、限流

微服务治理：
- 服务注册：启动时注册到注册中心
- 负载均衡：客户端侧负载均衡
- 熔断降级：Hystrix、Sentinel
- 限流：令牌桶、漏桶算法
- 超时控制：调用链路超时配置

部署与运维：
- 容器化：Docker 打包，Kubernetes 编排
- CI/CD：Jenkins、GitLab CI 自动化流水线
- 监控告警：Prometheus + Grafana
- 日志聚合：ELK、EFK

适用场景：
- 业务复杂度高、团队规模大
- 需要独立扩展某些模块
- 对部署频率和灵活性要求高

不适用场景：
- 业务简单、团队小（单体更合适）
- 对强一致性要求极高的金融交易系统

信创环境适配：Spring Cloud Alibaba + Nacos + Sentinel 是国产化微服务治理的优选方案。
